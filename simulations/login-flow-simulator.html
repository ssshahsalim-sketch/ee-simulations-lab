How "Login" Actually Works

Five layers are involved every time a user signs into a website or app — the browser, an encrypted network channel, the application server, the credential store (database), and a session/token mechanism that keeps the user "logged in" across pages. ① The Two Trips

Every login is really two separate events: (1) a one-time credential check where the server proves you are who you say you are, and (2) a repeating "remember me" check on every later page, using a token instead of your password again.

② Never Trust the Client

The server never trusts what the browser claims. It re-verifies identity from the session/token on every request — because anyone can edit browser JavaScript or spoof a request.

③ Passwords Are Never Stored

A well-built server never keeps your actual password — only a one-way hash of it (see the Password Security tab). Even the site operator cannot recover it.

    Password Security Lab

    This lab uses your browser's real cryptographic engine (SubtleCrypto SHA-256) so the hashes below are genuine — not simulated numbers — while staying 100% local and offline.

    ① Why Plaintext Storage Is Dangerous

    Stored as plaintext (bad practice):
    Anyone who reads the database — an attacker, a curious employee, a leaked backup — instantly has the real password, and probably the same password the user reused elsewhere.
    Stored as a SHA-256 hash (still not enough alone):
    Better — but identical passwords always produce the identical hash, so attackers use precomputed "rainbow tables" to reverse common ones.
    Stored as a salted hash — the real-world approach (bcrypt/argon2 style):
    Every account gets its own random salt, so two users with the same password get completely different stored hashes — rainbow tables become useless.

    ③ Brute-Force Cost, Visualised

    A fast hash function is bad for password storage — it lets attackers try billions of guesses per second. Purpose-built algorithms like bcrypt/argon2 add a deliberate "work factor" to slow every single guess down.

    A JWT (JSON Web Token) is just three Base64URL-encoded chunks joined by dots — header.payload.signature. Click a piece to see what's inside it.

    ◈ Standard Login Sequence (Summary)

    #StepDetail
    1TLS handshakeBrowser and server negotiate an encrypted HTTPS channel before any data is sent.
    2Form submissionUsername + password are POSTed over the encrypted channel — never in the URL.
    3LookupServer finds the account record by username/email.
    4Hash & compareEntered password is hashed with the account's stored salt/algorithm and compared to the stored hash.
    5Session/token issuedOn success, server creates a session (or signs a token) proving identity for future requests.
    6Cookie setResponse sets a Secure, HttpOnly, SameSite cookie (or the client stores a token).
    7RedirectBrowser is redirected to the authenticated area; the cookie/token is sent automatically on every request from here on.

    ◈ Common Hardening Measures

    Transport

    HTTPS everywhere (TLS 1.2+), HSTS header, no credentials ever in a GET/URL.

    Credential storage

    bcrypt / argon2 / scrypt with per-user salt; never plain SHA-256 or MD5 alone.

    Session/token

    HttpOnly + Secure + SameSite cookies; short token expiry with refresh tokens; server-side revocation list.

    Abuse prevention

    Rate limiting & account lockout/backoff, CAPTCHA on repeated failures, breached-password checks.

    Request forgery

    CSRF tokens on state-changing forms, SameSite=Lax/Strict cookies.

    Extra factor

    MFA/OTP/authenticator apps so a stolen password alone isn't enough.
